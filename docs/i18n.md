# Internationalization (Orca)

Two things live here: how the interface decides which language to speak, and
where the strings themselves come from.

Plane ships a translation catalogue for nineteen languages. Upstream, the only
way anyone reaches it is by opening Preferences and changing their own setting
— every profile is born speaking English. On a self-managed instance run by one
organization that is the wrong default for everybody at once. This fork adds an
instance-wide default so the product speaks the organization's language from the
first screen, without taking away anyone's ability to choose differently.

## Which language a screen renders in

Four sources, first match wins:

| Order | Source                            | Where it comes from                                                                 |
| ----- | --------------------------------- | ----------------------------------------------------------------------------------- |
| 1     | The person's stored choice        | `localStorage.userLanguage`, written when they pick a language or when their profile loads |
| 2     | The person's profile              | `Profile.language`, applied on sign-in                                              |
| 3     | The organization's default        | `DEFAULT_LANGUAGE`, published on `GET /api/instances/` as `config.default_language` |
| 4     | English                           | `FALLBACK_LANGUAGE` — the source catalogue, the only locale complete by definition   |

In practice:

- **Before sign-in** — the sign-in, sign-up and invitation screens, and the
  public space app — there is no profile, so the organization's default decides.
- **After sign-in**, the profile decides. A person who has never touched the
  setting has a profile that was born with the organization's default, so the
  two agree; a person who changed it keeps their choice.
- **On sign-out**, the stored preference is dropped and the interface returns to
  the organization's default. The next person to reach that browser is not the
  one who left, so the sign-in screen should not still be in their language.

The two async requests that carry a language — the instance configuration and
the user profile — can resolve in either order. `applyDefaultLanguage()` stands
down whenever a real preference has already landed, so the ordering does not
matter. It also never writes to `localStorage`: an organization default that
persisted itself would be indistinguishable from a personal choice, and a later
change to the setting would never reach anyone who had loaded the app once.

## Setting the default

**In god-mode**, under **Settings → General → Default language**. This is the
normal path. Saving invalidates the cached `/api/instances/` response, so the
change reaches the sign-in screen on the next load rather than after the
endpoint's two-hour cache window.

**By environment variable**, `DEFAULT_LANGUAGE`, which seeds the setting the
first time `configure_instance` runs. After that row exists, god-mode is the
authority and the variable is ignored — unless the instance runs with
`SKIP_ENV_VAR=0`, in which case the environment always wins and the god-mode
field has no effect. That is the same trade-off every other instance setting
makes; it is not specific to this one.

Accepted values are the catalogue's locale codes:

```
en  fr  es  ja  zh-CN  zh-TW  ru  it  cs  sk  de  ua  pl  ko  pt-BR  id  ro  vi-VN  tr-TR
```

Anything else — a typo, a bare `pt`, an underscore instead of a hyphen, the
right code in the wrong case — is read as `en`. Matching is exact because the
codes are the catalogue's own directory names, and a near-miss would be
silently ignored by i18next, which looks like the setting having no effect.

## Existing members

The default applies to profiles created after it is set. It does not reach back,
because `Profile.language` cannot tell somebody who deliberately chose English
from somebody who never opened the setting — both rows say `en`.

For a fresh instance that is fine. For one that already has members, there is an
opt-in one-off:

```bash
# Preview: how many profiles would move
python manage.py apply_default_language

# Write it
python manage.py apply_default_language --apply

# Or target a language without changing the instance setting first
python manage.py apply_default_language --apply --language pt-BR
```

It only touches profiles still holding `en`. Anyone who picked a language keeps
it. The caveat is the one above: a person who deliberately chose English is
swept along with everybody who never looked, and will have to set it again. Run
it once, shortly after setting the default, or not at all.

## How it is wired

Nothing here adds a column to a core model or patches an upstream call site,
per [FORK.md](../FORK.md).

| Piece                                                  | Does                                                                                                                 |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `plane/app/services/orca/language.py`                  | Reads and validates the setting. `get_default_language()` never raises — a bad value must not be able to stop sign-in. |
| `plane/app/services/orca/signals.py`                   | `post_save` on `Profile`: a new profile still holding the field default is given the instance default.                |
| `plane/app/apps.py`                                    | Registers that receiver in `ready()`.                                                                                |
| `plane/utils/instance_config_variables/orca.py`        | Declares `DEFAULT_LANGUAGE` so `configure_instance` seeds it.                                                        |
| `plane/license/api/views/instance.py`                  | Publishes `config.default_language`, normalized, batched into the existing configuration read.                        |
| `plane/db/management/commands/apply_default_language.py` | The opt-in rollout above.                                                                                          |
| `packages/i18n/src/core/set-language.ts`               | Separates applying a language from remembering it: `setLanguage`, `applyDefaultLanguage`, `clearLanguagePreference`.  |
| `packages/constants/src/language.ts`                   | A mirror of the locale list for consumers that must not boot i18next — the god-mode app.                             |

Four profile-creation paths exist upstream (the OAuth adapter, the magic-link
view, the redirection backfill, and the god-mode first admin). A receiver covers
all four; patching them would have been four merge conflicts on every upstream
sync for one behavior.

## What the API says when something fails

The Orca layer answers a failure with three fields:

```json
{ "error": "Organizational unit not found", "error_code": 4900, "error_message": "ORG_UNIT_NOT_FOUND" }
```

`error` is English and stays that way: it is what an API client, a log line or
`curl` reads. `error_code` is what the interface uses — it looks the number up
in `ORCA_ERROR_CODE_KEYS` and renders the catalogue string, so the person sees
the failure in their own language. `error_message` is the symbolic name, so a
human reading the response does not have to look the number up.

Translating on the server would mean gettext, a locale middleware and `.po`
catalogues that upstream does not have, plus a language the API would have to
guess for every caller. A code sidesteps all of it.

Codes live in the fork's own 4900 band, clear of upstream's `ERROR_CODES`
(4091-4702). **A code is permanent once shipped** — clients key off it, so
renumbering one changes which sentence somebody reads.

Adding a failure means four edits, and `test_orca_error_codes.py` fails until
all four are there:

1. `ORCA_ERROR_CODES` and `ORCA_ERROR_MESSAGES` in `plane/utils/orca_error_codes.py`
2. Return it with `orca_error("NAME")` or `orca_not_found("NAME")`
3. Map the number in `packages/constants/src/orca/error-codes.ts`
4. Add the catalogue key it points at, in all nineteen locales

On the client, `resolveOrcaErrorKey(error)` turns a rejected request into a
catalogue key or `undefined`. It deliberately does not supply a fallback: each
panel knows which generic line suits it.

```ts
message: t(resolveOrcaErrorKey(error) ?? `${OU}.try_again`),
```

The SCIM endpoints are the exception. They answer in the RFC 7644 envelope
Microsoft Entra ID expects, machine to machine, and nobody reads them on a
screen.

## The catalogue

Source of truth is `packages/i18n/src/locales/en/<namespace>.json`. Every other
locale mirrors it key for key.

Rules for translating — do-not-translate terminology, CLDR plural forms,
placeholder and tag preservation, per-locale punctuation and register — live in
[`.claude/skills/translate/SKILL.md`](../.claude/skills/translate/SKILL.md).
Read it before touching any file under `src/locales/`.

One commit per change, English source and all eighteen target locales
together. The Areas strings landed as two commits — source first, locales
after — but that was before `check:sync` gated the build; a source-only commit
is now a knowingly red one, and bisecting through it is worse than the larger
diff. Group by feature area instead, so each commit is one screen's worth of
strings rather than a whole sweep.

```bash
pnpm check:sync                                    # every locale vs. English
pnpm --filter @plane/i18n run sync:check           # same, human-readable report
pnpm --filter @plane/i18n run generate:types       # regenerate TTranslationKeys
```

`check:sync` runs in stage CI and in `pnpm check`. It compares key *presence*,
not value quality: copying the English string into a target locale passes the
check and ships English to that language. That is worse than leaving the key
missing, because nothing will ever flag it again.

### Known gap: plural forms in the existing catalogue

`check:sync` compares key presence, and nothing checks that a
`{count, plural, ...}` block carries the categories its language requires. A
sweep over the catalogue found **194 blocks that do not**, all predating this
work:

| Locale             | Blocks | What is wrong                                              |
| ------------------ | ------ | ---------------------------------------------------------- |
| cs, pl, sk         | 21 each | missing `few` and/or `many` — wrong word at 2-4 and 5+     |
| fr, it, pt-BR      | 21 each | missing `many`                                             |
| ua                 | 20     | missing `few` and/or `many`                                |
| ru                 | 19     | missing `few` and/or `many`                                |
| ro                 | 18     | missing `few`                                              |
| de                 | 11     | a spurious `few`, which German does not have               |

`ru/work-item.json` is the clearest example: `issue.label` has only `one` and
`other`, so two work items read "2 Рабочие элементы" where Russian wants
"2 рабочих элемента".

Strings added since carry the right categories — they are generated against a
per-locale CLDR table rather than written by hand. Fixing the 194 is a separate
sweep: it touches ten locales and no feature, and mixing it into a feature PR
would bury both. Worth doing before adding a plural-category check to CI, since
the check would fail on day one otherwise.

### The locale list exists in six places

Adding a language means touching all of them:

1. `packages/i18n/src/locales/<code>/` — the catalogue directory
2. `SUPPORTED_LANGUAGES` in `packages/i18n/src/constants/language.ts`
3. `TLanguage` in `packages/i18n/src/types/language.ts`
4. `LANGUAGE_CHOICES` in `packages/constants/src/language.ts`
5. `TLanguageCode` in the same file
6. `SUPPORTED_LANGUAGES` in `plane/app/services/orca/language.py`

`test_default_language.py` parses all six and fails if they disagree, so
forgetting one is a red build rather than a language that silently cannot be
selected.
