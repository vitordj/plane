# Plane Compose — notes for Orca (item 4.1 / A5)

Source: [Plane Compose developer docs](https://developers.plane.so/dev-tools/plane-compose),
[PyPI `plane-compose`](https://pypi.org/project/plane-compose/) (0.5.2, 2026-07-02),
product page `https://plane.so/plane-compose`. Read 2026-09-10.

This file is the decision record for **A5**, not a substitute for the
upstream docs. When the two disagree, the packaged CLI is the authority.

## Decision (F12, confirmed)

**Compose versions project schema in Git. Process instances always go through
the public automation API (`POST /api/v1/orca/…/work-items/`).**

Compose is local-first Projects-as-Code: YAML is the declared intent, the
Plane instance is the remote, `.plane/state.json` is only the sync map
(local id → remote UUID, content hashes). It is not a workflow engine and it
does not know what an Orca area is.

That is exactly F12. The reading did not contradict it, so F12 stays closed.

What Compose is for, in this fork:

- states, labels, work-item types, workflows, feature flags of the **pilot
  project**, reviewed as YAML;
- cloning that schema into another workspace;
- CI `plane schema validate` / `plane schema push --dry-run`.

What Compose is **not** for:

- creating a run of onboarding (or any other process);
- assigning an area, an executor, or an SLA;
- being the source of truth for `ProcessInstanceReference`.

The orchestrator (item 4.4, other repository) talks to `/api/v1/orca/` with
`Idempotency-Key = "{source}:{instance}:{step}:{event_id}"`. Compose never
sees those calls.

## A5 — the questions the item asked

### Authentication

A **connection** is `(server URL, auth type, token)`. Types: `pat` or
`workspace`. Interactive: `plane auth login`. CI:

```bash
plane auth login \
  --server-url https://plane.example.com \
  --auth-type pat \
  --token "$PLANE_TOKEN" \
  --workspace acme
```

Credentials live under `~/.config/plane-compose/`, never in `plane.yaml`.
Self-hosted uses `--server-url` or `PLANE_API_URL`.

### Work-item fields (Compose `work/workitems.yaml`)

Documented: `id` (local stable key), `title`, `type`, `state`, `priority`,
`labels`, `assignees`, `watchers`, `start_date`, `due_date`, `description`,
`parent`, `blocked_by`, `blocking`, `duplicate_of`, `relates_to`,
`properties`.

**There is no field for an area, an organizational unit, a routing state, or a
process instance.** Assignees are emails of project members. That is the
native Plane model, which is the opposite of what the public Orca API is for
(the area decides who).

### Re-push with the same id

The local `id` is the tracking key. A second `plane push` with the same `id`
and changed title/state is an **update of the same remote work item**, not a
create — provided `.plane/state.json` still maps that id to the remote UUID.

Without `id`, Compose may derive a key from content. Changing the title then
looks like a new item and **duplicates remotely**. Anything generated by a
program (including an orchestrator that was tempted to push work through
Compose) must use a stable `id`. That is another reason instances stay on the
REST API: the Orca binding already _is_ that stable key
(`external_source` + `external_id`).

`plane state reset --force` forgets the map; the next push will try to create
again. Do not reset state in CI.

### State file

`.plane/state.json` is written by the CLI. It is not a source of business
truth. Agents must not edit it to "fix" a sync. Recovery is
`plane schema import` then `plane pull`.

### Area / custom properties on Plane CE 1.4.x

Compose documents custom properties on work-item types (`schema/types.yaml`
→ `properties`). **Plane CE 1.4.x, which this fork is based on, does not have
custom properties.** There is therefore no CE field an operator could fill
with an area slug and have Compose push it.

The only source of truth for the area on a work item remains
`IssueOrganizationalUnit`, written by the public API or the UI.

## What this means for a re-push that omits the area

Compose cannot omit or include an area: the field does not exist. A work item
pushed as schema/work through Compose lands in the project with no Orca
routing. The coordinator never sees it in the area queue. That is acceptable
for seed/demo issues in a template; it is not acceptable for a live process
run. Hence F12: instances via REST.

## Pilot project schema (example)

Minimal Compose tree for a compliance/onboarding project. Schema only — no
`work/` entries for live clients.

```yaml
# plane.yaml
type: project
workspace: acme
project:
  key: ONB
  name: Onboarding
  network: private
  timezone: UTC
defaults:
  type: Task
  workflow: default
```

```yaml
# schema/states.yaml
states:
  Backlog:
    group: backlog
    color: "#858585"
    allow_issue_creation: true
    is_default: true
  Todo:
    group: unstarted
    color: "#d1d5db"
  In Progress:
    group: started
    color: "#f59e0b"
  Awaiting review:
    group: started
    color: "#8b5cf6"
  Done:
    group: completed
    color: "#22c55e"
  Cancelled:
    group: cancelled
    color: "#ef4444"
```

```yaml
# schema/labels.yaml
labels:
  - name: onboarding
    color: "#3b82f6"
  - name: aguardando-validacao
    color: "#F59E0B"
```

`aguardando-validacao` is the label `complete/?mode=automatic_with_review`
creates on demand when the area has no `review_state`. Declaring it in
Compose keeps the board legend in Git.

Push with `plane schema validate && plane schema push`. After the first push,
the remote UUID is written into `plane.yaml`; do not copy that UUID into
another environment.
